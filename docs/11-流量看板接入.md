# 11 · 流量看板接入（官网 → 中控台）

> 目标：官网 jinyoudata.com 的访客、留资、会员数据，实时出现在中控台【官网流量】里。
> 本文只讲「要做什么、怎么验」，口径定义见中控台页面里的「数据源与口径说明」。

---

## 0. 一句话架构

```
浏览器 ──POST /api/track──> 官网 Edge Function ──service key──> Supabase(page_views)
                                                                    │
中控台（Python 服务端）──REST/service key──────────────────────────────┘
        └──直连被拦时──> 官网 /api/admin/traffic（只搬运，不聚合）──┘
```

**聚合只发生在中控台一处**（`cloud.py`），官网中转接口只做「按条件把行取出来」。
两边各算一遍，迟早会打架。

## 1. 建表（必做，一次）

Supabase Dashboard → SQL Editor → 整段粘贴运行：

```
supabase/migrations/0011_page_views_visitor.sql
```

它做三件事，全部幂等：

| 内容 | 说明 |
|---|---|
| 建 `page_views`（若 0010 没跑过）并补齐 5 列 | `visitor_id` / `device` / `source` / `utm_medium` / `utm_campaign` |
| 建索引 | 按天、按人（`visitor_id, created_at`）、按页面、按渠道 |
| 开 RLS | 只有 `service_role` 能读写，`anon` 一行都读不到 |

> **为什么必须补 `visitor_id`**：没有它就算不出 UV。同一个人看三次会被当成三个访客，
> 漏斗第一步直接失真。补上之前，中控台会把 UV 标成「近似值」并提示去跑这条迁移。

跑完自检：

```sql
select count(*) as rows, count(distinct visitor_id) as visitors from public.page_views;
select * from public.v_traffic_daily limit 7;
```

本次改了 4 个文件，`git push` 到 `main` 即触发 GitHub Actions → Cloudflare Pages：

```bash
git add -A && git commit -m "流量看板：page_views 补 visitor_id 等列，埋点带上 UTM 与匿名访客 ID，新增只读取数中转"
git push origin main
```

部署完成判断：Actions 变绿 + 下面这条命令返回 `stored: true`。

```bash
curl -s https://jinyoudata.com/api/track \
  -H 'Content-Type: application/json' \
  -d '{"type":"page_view","path":"/__deploy_check","visitor_id":"deploycheck01","device":"桌面端"}'
# 期望 {"ok":true,"stored":true}
```

新版返回带 `uv_capable` 字段：`uv_capable:true` 才说明 `visitor_id` 真的落库了。
`uv_capable:false` 看 `dropped_columns` 里被裁掉的列名；`stored:false` 再看 `error`。
看到 `Could not find the table` 说明 0010 和 0011 都没跑。

## 3. 埋点字段契约

`POST /api/track`（同源，无需 CORS）：

| 字段 | 必填 | 说明 |
|---|---|---|
| `type` | ✅ | 固定 `"page_view"` |
| `path` | ✅ | 路径，**去掉 `utm_*`/`gclid`/`fbclid`**，否则同一页会被拆成上千种 |
| `referrer` | | 来源域名；站内跳转传 `internal`，无来源传 `direct` |
| `utm_source` / `utm_medium` / `utm_campaign` | | 渠道归因；缺省时前端用首触（localStorage）兜底 |
| `visitor_id` | | 匿名 UUID，来自 `localStorage.jinyou_vid`，一次生成长期复用；只用于「同一个人算一次」，与账号无关 |
| `device` | | `移动端` / `桌面端` |
| `ts` | | 客户端 ISO 时间（仅参考）；`created_at` 一律用服务端时钟，保证 UTC+8 当日窗口可信 |

同端点也接收行为事件（`form_submit` / `wechat_click` / …）→ 写 `events` 表。

**跨域场景**：若以后把站点和中控台拆到不同域名，把组件的
`NEXT_PUBLIC_TRACK_ENDPOINT` 指向中控台 `/api/track` 即可（服务端已开 CORS 与预检）。

## 4. 中控台侧配置

中控台自动按顺序找配置，命中即用：

1. 环境变量 `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` / `SUPABASE_RELAY_URL` / `DASH_ADMIN_TOKEN`
2. `supplier_dashboard/.supabase.env`
3. 同级官网仓库的 `.env.local`（自动发现）

本机已能自动发现，无需额外配置。服务 key **只留在服务端**，接口响应里项目地址也是脱敏的。

## 5. 验收步骤（5 分钟）

1. 手机连 4G（不要用公司 Wi-Fi，避免被网关缓存），打开 `https://jinyoudata.com/?utm_source=xhs_test`
2. 点开任意两个页面，比如 `/products`、`/insights`
3. 回到中控台【官网流量】，30 秒内应看到：
   - 今日 UV 保持 1（同一 `jinyou_vid` 只算一个访客）、PV 随刷新持续增加
   - 来源里出现「小红书」（来自 `utm_source`）
   - 热门页面里出现 `/products`、`/insights`
4. 点「数据源自检」，`page_views / leads` 应显示「✓ 可读」，
   `visitor_id / device / source` 应显示「✓ 已就绪」
5. 若 UV 仍显示「近似」，说明第 1 步的迁移没跑成功

## 6. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 自检里 `page_views` 显示「表不存在」 | 迁移没跑 | 执行 0011 |
| 自检里字段显示「缺列（降级可用）」 | 只跑了 0010 | 执行 0011，历史行不会被改，新行才有 `visitor_id` |
| 顶部提示「UV 目前无法精确去重」 | `visitor_id` 列不存在 | 执行 0011 + 0012，并刷新 PostgREST schema |
| **UV 恒等于 PV** | 见下方第 8 节：线上只跑了早期版 0011，缺 `utm_medium` 一列，导致整包退回四列、`visitor_id` 全 null | 执行 0012 或直接依赖新版 `/api/track` 的渐进裁剪；再清空今日脏数据 |
| 今日有 N 行「未带访客 ID」 | 修复埋点前留下的测试记录 | 点中控台「清空今日测试数据」，或执行 0012b |
| 漏斗「留资」大于「访客」 | leads 里有埋点上线前的存量留资 | 正常，页面已注明；等新流量进来自然对齐 |
| 自检显示「本机不可达」 | 办公网拦截 `*.supabase.co` | 配 `SUPABASE_RELAY_URL` + `DASH_ADMIN_TOKEN` 走中转 |
| 数字一直是 0 但官网能打开 | 埋点没发出 | 浏览器控制台看是否有 `/api/track` 请求；确认 `<PageViewTracker />` 在 layout 里 |

## 7. 回滚

埋点整体是旁路，出问题不影响官网正常访问：

- 只想停采集：把 `layout.tsx` 里的 `<PageViewTracker />` 注释掉再部署
- 只想停中转：中控台 `SUPABASE_RELAY_URL=off`
- 数据不清：`page_views` 与业务表无外键关联，随时可单独清空

## 8. 2026-11-15 · UV 去重失效修复（真实故障复盘）

### 现象
自检面板里表、`visitor_id` 等字段全是绿勾，但今日 UV=29 / PV=29，
同一部手机每刷新一次 UV 就 +1，完全没去重。

### 根因（不是前端没生成 ID）
逐列探测线上 `page_views` 得到：

```
visitor_id   ✓ 存在      device ✓      source ✓      utm_campaign ✓
utm_medium   ✗ column page_views.utm_medium does not exist
```

线上 SQL Editor 执行的是**早期版 0011**（当时还没加 `utm_medium`），
后来仓库里的 0011 补上了这一列，但没人在云端重跑。
而旧版 `/api/track` 是「全字段 → 核心四列」两段式：只要 PostgREST 报一个
列不存在，就把整包丢掉、只写 `path/referrer/utm_source/created_at`，
**连本来存在的 `visitor_id` 也一起砍了** → 29 行全是 `null`。
中控台 `uv_of()` 当时又有一条「集合为空就退化成 `len(items)`」的兜底，
于是 UV 直接等于 PV。三处叠加，才出现「字段看着齐、UV 却不去重」。

### 修好的三处
1. **写入**：`/api/track` 改成按报错点名的列**逐个裁剪**，
   裁剪顺序 `utm_medium → utm_campaign → device → source → visitor_id`，
   `visitor_id` 排最后。只要表里能写，UV 就一定算得出来。
   响应新增 `uv_capable` / `dropped_columns`，方便一眼验写入质量。
2. **前端**：`visitor_id` 固定存 `localStorage.jinyou_vid`（标准 UUID），
   旧 key `qipei_vid` 自动迁移；每次上报都读这个固定值，绝不现生成。
3. **聚合**：中控台严格 `COUNT(DISTINCT visitor_id)`，空 ID 的行贡献 0 个访客，
   **不再拿 PV 冒充 UV**；今日窗口用 UTC+8 半开区间
   `[北京 00:00, 次日 00:00)`，与 SQL 视图 `at time zone 'Asia/Shanghai'` 同源。

### 需要人工执行的 SQL（Supabase SQL Editor）
| 文件 | 作用 | 是否必须 |
|---|---|---|
| `0012_fix_uv_dedupe.sql` | 补 `utm_medium` + `NOTIFY pgrst, 'reload schema'` + 重建 UTC+8 视图 | 推荐（不跑也能去重，只是少一个投放媒介字段） |
| `0012b_purge_today_test_traffic.sql` | 清空北京时间今天的测试流量 | 想从 0 UV 开始就跑 |

**注意 `NOTIFY pgrst, 'reload schema'`**：只 `ALTER TABLE ADD COLUMN` 而不刷新
PostgREST 的 schema cache，写入仍可能报「column not found in schema cache」。

### 不想跑 SQL 的替代路径
- 补列：新版 `/api/track` 会自动裁掉 `utm_medium`，`visitor_id` 照常落库。
- 清数据：官网 `DELETE /api/admin/pageviews?scope=today`（带 `x-admin-token`），
  或中控台【官网流量】→「清空今日测试数据」按钮（先 dry-run 报数再二次确认）。

### 验收
```bash
curl -s https://jinyoudata.com/api/track -H 'Content-Type: application/json' \
  -d '{"type":"page_view","path":"/__deploy_check","visitor_id":"deploycheck01","device":"桌面端"}'
# 期望 {"ok":true,"stored":true,"uv_capable":true,"dropped_columns":[]}
```
然后清空今日数据，用**同一部手机**连续刷新 3 次：
UV 应保持 1，PV 应从 1 → 2 → 3。自检面板「今日未带访客 ID」应为 `0 / 3 行`。
